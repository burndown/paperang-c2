# 喵喵机 C2 通信协议参考

[English](PROTOCOL.md)

本文说明如何用自己的代码驱动 Paperang C2 热敏打印机（国内名称“作业帮喵喵机 C2”）。打印机的蓝牙名为 `Paperang_C2_xxxx`，USB 厂商/产品号为 `34d6:01a2`。

C2 使用以 `0xA5` 开头、`0x5A` 结尾的帧格式，本文称为**协议 2**。它不是早期开源工具实现的老款喵喵机 `0x02 ... 0x03` 帧，C2 对老帧完全不响应（见[走过的死路](#走过的死路)）。

> **非官方。** 本文是作者在自己的设备上做的独立互操作性研究，与打印机厂商没有任何关联，也未获其认可或支持。产品名称和商标归各自所有者。协议是通过真机实验以及观察厂商官方 App 的行为整理出来的，文中不包含、也不转载任何厂商代码。

## 测试范围与可信度标记

标记 **[事实]** 的内容在真机上验证过：一台 C2，固件 `01.00.22`，纸宽设置为 110 mm、实际装 4 英寸（101.6 mm）卷纸，分别从 macOS 和 Linux 通过经典蓝牙驱动。标记 **[推断]** 的内容来自对厂商 App 行为的观察，尚未在打印机上确认。其他 Paperang 型号、其他固件版本和其他传输方式均未测试。

## 传输

**经典蓝牙 SPP [事实]。** 打印机在 RFCOMM 通道 1 上提供串口服务（SDP 名 `SPP slave`）。帧按原始字节直接写入，没有额外加密，也没有额外分包层。

**同一时间只接受一个主机 [事实]。** 打印机只接受一个蓝牙连接。手机上的厂商 App 连着它时（即使 App 在后台），其他主机连不上。

**macOS 说明 [事实]。** macOS 把 C2 识别为打印机类设备，它生成的虚拟串口（`/dev/cu.Paperang_C2_xxxx`）永远连不上；主机必须通过 IOBluetooth 框架自行打开 RFCOMM 通道，进程需要蓝牙权限。Linux 上直接用 RFCOMM socket 连通道 1 即可。

**USB（未验证）。** USB 是打印机类接口，批量输出端点 `0x01`，批量输入端点 `0x81`。写入不报错，但老协议以及 ESC/POS/TSPL/CPCL/ZPL 都没有任何回应。协议 2 的帧**没有**在 USB 上试过，USB 能否用这个协议仍是未知数。

## 帧格式 [事实]

```
A5 01 | len (LE16) | payload | crc32 (LE32) | 5A
```

`len` 是 payload 长度。CRC 只覆盖 payload，算法是标准反射 CRC-32（表多项式 `0xEDB88320`），但初始值取固定密钥 `0x35769521` 而不是 0，Python 写法为 `zlib.crc32(payload, 0x35769521)`。测试中收到的所有回包都通过了这个校验。与老协议不同，密钥是固定的，不需要“设置 CRC 密钥”的握手。

**请求 payload：**

```
group (1) | cmd (1) | dir = 01 | dataLen (LE16) | data
```

**回复 payload：**

```
group (1) | cmd (1) | dir = 02 | contentLen (LE16) | content
content = status (1) | valueLen (LE16) | value
```

`status` 为 `1` 表示成功，`3` 表示非法指令。打印机发出的 `dir = 01` 的 payload 是设备主动上报的事件。多参数命令用 TLV 编码：`tag (1) | len (LE16) | value`，可重复。

所有多字节整数均为小端序。

## 最小示例

帧 `a5010500011501000041d235195a` 就是探测帧：“查询协议/固件版本”（group `01`，cmd `15`，无数据）。**[推断]** 厂商 App 每次连接都先发它，根据有没有回包判断打印机是否使用协议 2。下面这段独立代码构造该帧，并解析一个符合预期格式的回包。示例中的回包字节是按上文格式、以固件 `01.00.22` 为值计算出来的，不是抓包记录。

```python
import struct, zlib

KEY = 0x35769521

def frame(payload: bytes) -> bytes:
    return (b"\xa5\x01" + struct.pack("<H", len(payload)) + payload
            + struct.pack("<I", zlib.crc32(payload, KEY)) + b"\x5a")

def request(group: int, cmd: int, data: bytes = b"") -> bytes:
    return frame(bytes((group, cmd, 1)) + struct.pack("<H", len(data)) + data)

probe = request(0x01, 0x15)
assert probe.hex() == "a5010500011501000041d235195a"

def parse(buf: bytes):
    assert buf[0] == 0xA5 and buf[-1] == 0x5A
    (n,) = struct.unpack_from("<H", buf, 2)
    payload = buf[4:4 + n]
    (crc,) = struct.unpack_from("<I", buf, 4 + n)
    assert crc == zlib.crc32(payload, KEY), "bad CRC"
    group, cmd, direction = payload[:3]
    content = payload[5:5 + struct.unpack_from("<H", payload, 3)[0]]
    status, vlen = content[0], struct.unpack_from("<H", content, 1)[0]
    return group, cmd, direction, status, content[3:3 + vlen]

reply = bytes.fromhex("a50110000115020b0001080030312e30302e3232873507995a")
print(parse(reply))   # (1, 21, 2, 1, b'01.00.22')
```

实际使用时，打开到通道 1 的 RFCOMM 连接，写入 `probe`，读到一个完整帧后交给 `parse`。

## 指令表

### 查询 [事实]

以下查询在测试机上都返回了成功的回包。

| 查询 | group/cmd | 返回值 |
|---|---|---|
| 协议/固件版本 | 01/15 | ASCII，如 `01.00.22` |
| 序列号 | 01/02 | ASCII，如 `C200H0XXXXXXXX` |
| 软件版本 | 01/07 | ASCII |
| 产品类型 | 01/08 | TLV：tag 1 = 类别，tag 2 = 型号字符串 `C2` |
| 电量 | 01/0B | LE16，除以 10 为百分比 |
| 最大包长 | 01/14 | LE16，C2 为 `1297` |
| 最大缓存 | 01/20 | 回复值 `08 00`（8）。含义不明，App 会读出保存，但看起来没有使用。 |
| DPI | 05/04 | LE16，C2 为 `300` |
| 支持纸宽 | 05/02 | TLV，每项 LE16 毫米，C2 为 `57`、`79`、`110` |
| 加热点数 | 05/05 | LE16，110 mm 设置下为 `1248` |
| 浓度 | 05/10 | 1 字节 |
| 热敏头信息 | 05/01 | JSON `{"TPInfo": {...}}`，含 `TPCurrentSize`（当前纸宽设置，mm）和 `TPDevDPI` |
| 各纸宽打印参数 | 05/28 | JSON `{"TPSizeInfo": [{"PaperWidth", "HotSpot", "OffsetStart"}, ...]}` |

## 确定打印宽度 [事实]

不要写死 384 或 576 点。先查 `05/01`，读 `TPInfo.TPCurrentSize`（打印机当前设置的纸宽，mm），再查 `05/28`，在 `TPSizeInfo` 里找 `PaperWidth` 相同的一项。其中 `HotSpot` 是每行点数，`OffsetStart` 要写进每个数据帧。测试机上的值：

| PaperWidth (mm) | HotSpot（点） | OffsetStart |
|---|---|---|
| 57 | 576 | 0 |
| 79 | 864 | 0 |
| 110 | 1248 | 0 |

**物理纸宽可能比报告的窄。** 打印机设置为 110 mm（1248 点）、实际装 4 英寸（101.6 mm）卷纸时，打印一排不同位置的空心框测得：第 0 点贴着纸的左边，大约第 1200 点之后的内容印到纸外（框的右边线丢失，一个字符被切掉一半）。固件无法知道实际卷纸宽度，所以主机应按真实纸宽限制可打印区域，不能只信 `HotSpot`。发送的图像仍须是 `HotSpot` 点宽，只是把够不到的列留白。

## 打印流程 [事实]

1. （可选，未验证）设浓度 `05/11`。
2. 开始打印 `05/19`。
3. 数据帧 `05/1B`，序号从 1 开始。
4. 结束打印 `05/1A`。
5. 走纸 `05/16`，数据 `00 00`。

这些帧背靠背连续发出，之后再读回包并核对确认数量（见[时序规则](#时序规则-事实)）。

### 数据帧结构

```
payload = 05 1B 01 | outerLen (LE16) | outer
outer   = seq (LE16，从 1 起) | innerLen (LE16) | inner
inner   = 01 | width/8 (LE16) | offsetStart (LE16) | 00 | chunkLen (LE16) | chunk
```

整个 payload 再按普通的 `A5 01 ... 5A` 帧封装。`width` 是 `HotSpot`，`offsetStart` 是 `05/28` 中的 `OffsetStart`。`inner` 开头的 `01` 和中间的 `00` 含义不明，按常量发送。

### 图像格式

位图为 1 位/点，高位在前，**黑 = 1**，每行补齐到整字节，不压缩。各行从上到下拼接后再切块。不压缩的数据能正常打印是验证过的；C2 永远不走 App 的压缩路径则是 **[推断]**（App 看起来把 C2 排除在压缩路径之外）。

### 分块规则

设 `rowBytes = width / 8`，`maxLen` 取自查询 `01/14`，则块大小是不小于 `maxLen - 2 * rowBytes` 的最小的 `rowBytes` 整数倍。C2 在 1248 点时：`rowBytes = 156`，`maxLen = 1297`，`1297 - 312 = 985`，所以每块 `7 * 156 = 1092` 字节（7 行）。最后一块装剩余的行。

## 时序规则 [事实]

这一节最花时间才弄清楚，也比本文其他内容都重要。

**确认只表示“收到”，不表示“印完”。** 数据帧、结束打印、走纸的回包都在纸真正走完之前就回来了。没有“打印完成”事件或状态：状态查询 `05/0D` 和 `01/20` 在打印前、中、后的值都不变。

**过早断开会丢掉没印完的行。** 打印机缓存里还有没印出的数据时断开蓝牙，这些数据会被丢弃。一次实测中，一个 28 mm 的任务在最后一个确认后立即断开，丢了开头几个帧；保持 1.8 秒仍差一两帧；保持 3.2 秒才完整。所以发完后要保持连接，直到纸应当走完。参考代码从任务开始计时，等待 `1.5 秒 + 长度mm / 8` 秒；8 mm/s 有意比实测约 10 mm/s 更保守。

**断开后约 1 秒内重连会被重置。** 断开 0.3 秒后重连必定失败，超过 1 秒则正常。参考代码在两次连接之间至少间隔 1.5 秒。注意有些主机的蓝牙协议栈在进程退出后还会把链路保持一会儿，所以“断开”应指链路真正断掉，而不只是进程关掉了 socket。

**背靠背发送，不要逐帧锁步。** 厂商 App 把开始、全部数据帧、结束、走纸连续写出，从不逐条等待确认。测试中逐帧等确认再发下一帧，会在帧之间留下间隙并丢帧。应当全部发完，再读回包，核对数据确认数是否等于发出的数据帧数。

**不需要流控。** 打印机缓存可以接住整个任务：195 个数据帧在约 2.5 秒内写完没有问题。

## 未验证 / 未解决

**设备认证。** **[推断]** 厂商 App 连接后会发 `01/17`（带随机串），把回复转发给厂商服务器，再发 `01/1F`，失败就断开。**[事实]** 测试中完全没有做这一步，C2 照常打印，所以认证看起来是 App 侧的限制，而不是固件强制。以后的固件可能会改变这一点。

**纸张识别。** NFC 纸张标签以及服务器端的纸张类型校验都没有涉及。

**浓度与走纸参数。** `05/11` 的回包、浓度取值范围、非零走纸长度均未测试。

**其他固件、型号与 App 版本。** 只测试了一台 C2 的 `01.00.22` 固件。厂商 App 的国内版和国际版对 C2 的处理可能不同，这里只观察了其中一个版本的行为。

**USB。** 协议 2 在 USB 打印机类接口上尚未尝试。

**未知常量。** 数据帧内层头部的 `01` 和 `00` 字节，以及 `01/20` 返回值的含义，都还不清楚。

## 走过的死路

老协议（`0x02 ... 0x03` 帧，CRC 密钥 `0x35769521` 或 0，384/576 点宽）、ESC/POS、TSPL、CPCL、ZPL，对 C2 无论走蓝牙还是 USB 都没有任何回应。关键转折是注意到厂商 App 连接后**先发 `0xA5` 探测帧**，只有打印机不回应时才降级到老协议。
